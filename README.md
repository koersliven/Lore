# Lore

> 管理代码中的 WHY。

## 问题

**Git 解决了代码的版本管理，但代码本身只描述 HOW。**

Git 记录的是 who + what + when —— "谁在什么时候改了什么"。

但它不记录：
- **WHY** — 为什么这么改
- **WHERE** — 配置在哪里
- **WHICH** — 多条路径用哪条
- **FLOW** — 端到端流程是什么

这些信息不在代码里，不在 commit message 里，在开发者的脑子里。

**人走了，WHY 就死了。**

## 我们的愿景

**让隐性知识随代码一起传承。**

当前 AI coding 工具的最大瓶颈不是能力，而是上下文。你的 agent 智商 200，但每次都是第一天上班。它写出了技术上完全正确、但业务上可能致命的代码。

区别不在编码能力，在上下文的积累深度。

Lore 解决一个问题：**让 agent 从"孤立空间的天才"变成"持续在场的团队成员"。**

不是"又一份文档规范"。是**一套让隐性知识在开发过程中自动流出、结构化沉淀、随代码传播的机制。**

## 核心类比

```
Git (2005)              Lore (2026)
────────────            ────────────────────────────
记录: who + what        记录: WHY + WHERE + WHICH + FLOW
载体: code diff         载体: .lore/
传承: 代码变更历史        传承: 开发者脑中的知识
局限: WHY 在人脑里       突破: WHY 随代码一起传播
```

## 它是怎么工作的

```
开发者与 agent 讨论需求
  → agent 自动识别对话中的知识信号（WHY / CONSTRAINT / ARCHITECTURE）
  → 静默写入缓冲区，不中断对话
  → 用户暂停时，自动整理为增量文件
  → 知识随代码一起 git push
  → 任何人 clone 这个项目，就继承了所有积累
```

**知识通过 git 传播，和代码享受同等待遇——版本化、可 review、可回滚、可协作。**

## 知识质量保障

知识会积累，但也会出错。我们有三层质量保障：

### 1. 来源追溯

每条知识增量都包含：
```yaml
author: 谁说的
timestamp: 什么时候说的
trigger: 什么场景下说的（对话 / commit / 手动）
confidence: 置信度（high / medium / low）
验证状态: unverified → verified / challenged
```

### 2. 冲突检测

`/evolve` 编译快照时自动检测新旧知识矛盾：
- 不自动覆盖 → 标记 `[CONFLICT]`
- 保留双方记录 → 等待人工裁决
- 低置信度知识不进入快照 → 标记"待验证"

### 3. Git Review

增量文件随代码一起提交，天然支持 code review：
- 团队成员 review 知识增量
- 确认 → 验证状态变为 verified
- 提出异议 → 标记 challenged，触发冲突解决

## 编辑前防护

当你修改一个在 `.lore/` 中有知识沉淀关联的文件时：

```
⚠️ 此文件有相关知识沉淀：
[DECISION] buffer flush 阈值基于知识条目数 (利普, 2026-04-23)
  原因: 按轮数不准确，5 轮可能只有 2 条知识
你确定要修改吗？如果修改，请说明原因。
```

**修改历史的人，必须先了解历史。** 你的解释本身会被记录为新的知识。

## 快速开始

### 1. 初始化（~10 分钟）

```bash
npx lore init
```

agent 会问你关于项目的 5 类问题：外部依赖、配置、数据层、业务背景、隐式契约。回答完，agent 就对项目有了**最低可用的理解水平**。

### 2. 正常开发

什么都不需要额外做。agent 在日常开发中自动积累知识。

### 3. 查看积累

```
.lore/
├── snapshot.md           ← 编译后的项目全景（agent 入场时读取）
├── increments/           ← 每次开发产生的知识增量
│   ├── 2026-04-23_payment-timeout.md
│   └── 2026-04-25_order-refactor.md
│   └── archive/          ← 已编译的旧增量
└── config.yaml           ← 框架配置
```

```
        对话中自然流出              commit 后              主动引导提问
     ┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
     │ 用户纠正 agent    │    │ agent 提取 WHY   │    │ init 阶段问答    │
     │ 用户解释设计原因  │    │ 提取 IMPACT      │    │ 获取人脑知识      │
     │ 用户提到约束      │    │ 提取 CONSTRAINT  │    │ 外部依赖/业务场景 │
     └────────┬─────────┘    └────────┬─────────┘    └────────┬─────────┘
              │                       │                       │
              ▼                       ▼                       ▼
     ┌─────────────────────────────────────────────────────────────┐
     │              .lore/ 知识库（随代码共存）                        │
     │                                                             │
     │  snapshot.md  ← agent 的项目理解（长期记忆）                   │

                           │ git push

              全团队成员 + 任何 AI 工具继承
```

## 记录什么

不是所有代码变更都值得记录。只记录代码无法表达的信息：

| 类型 | 含义 | 示例 |
|------|------|------|
| **DECISION** | 设计选择及原因 | "选 MetaQ 不用定时任务因为要分布式" |
| **CONSTRAINT** | 不可违背的规则 | "这里不能改，上次改了出线上事故" |
| **ARCHITECTURE** | 系统关系和流程 | "订单创建后发两条 MQ 给库存和支付" |
| **EXTERNAL** | 外部依赖信息 | "AbilityExpand.predictCategory: Boolean" |

不记录：变量重命名、格式调整、纯粹的 bug fix —— 代码 diff 已经表达了。

## 框架架构

Lore 不是一款软件，而是一套可注入的**协议和配置**：

```
hooks/     — 6 个事件驱动触发器（Stop、Commit、SessionStart/End、PreToolUse×2）
skills/    — 3 个 Agent 技能（/init-context、/digest、/evolve）
templates/ — 增量文件模板、配置模板、CLAUDE.md 注入规则
spec/      — 知识分类和提取标准
```

用户在项目中安装后，agent 在日常开发中自动执行知识积累，开发者几乎无感。

完整架构图见 [architecture.md](architecture.md)。
数据流图见 [dataflow.md](dataflow.md)。

## 度量

**改造前**：理解一个核心流程 = 3 个 Agent × 5 分钟 = $12, 25 分钟
**改造后**：理解一个核心流程 = 读 1 个 snapshot = $0.05, 10 秒

更重要的是：**第 100 次迭代时，agent 对项目的理解决远优于第 1 次。** 因为每次开发都在积累知识。
