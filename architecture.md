## 四、知识分类与提取规则

```
┌─ 对话/开发场景 ──────────────────┬─ 分类 ─────┬─ 判断信号 ───────────────────────────────┐
│ "不对，这个不能这么改，因为..."     │ DECISION   │ 用户纠正、解释了设计原因                    │
│ "上次有人改了这里出了线上事故"     │ CONSTRAINT │ 不能碰的东西、不可违背的规则                  │
│ "这个流程是先...然后...最后..."   │ ARCHITECTURE│ 系统关系、端到端流程描述                     │
│ "这个类定义在外部 JAR 里..."      │ EXTERNAL   │ 外部依赖的关键信息                          │
│ "帮我写个单元测试"               │ 噪音       │ 无 WHY 层面，代码本身已表达                   │
│ "修了个空指针"                   │ 噪音       │ 纯粹的 bug fix，无架构意义                   │
└──────────────────────────────────┴────────────┴──────────────────────────────────────────┘

提取质量过滤（/digest 执行时）:
  • 合并相关条目 → 多个条目关于同一主题 → 整合为一个连贯章节
  • 冲突消解     → 新旧知识冲突 → 标记冲突，保留双方
  • 过滤噪音     → 纯粹的格式/变量名调整 → 丢弃
  • 模式识别     → 反复出现的主题 → 提升为 snapshot 级知识
```

```
┌─ 知识产生 ───────────────────┬─ 质量保障 ───────────────────────────────┬─ 最终状态 ─┐
│                              │                                          │           │

│                              │    ┌─────────────────┐                   │           │
│ 内容: buffer flush 阈值      │──→ │ 置信度: high     │ ── 直接进入快照    │  verified │
│         基于知识条目数        │    └─────────────────┘                   │           │
│                              │                                          │           │
│ 来源: 张三, 2026-04-25       │    ┌─────────────────┐                   │           │
│ 场景: 开发对话（新人）        │──→ │ 置信度: low      │ ── 待验证区       │ unverified│
│ 内容: 这个接口是同步的        │    └─────────────────┘                   │           │
│                              │                                          │           │
│ 来源: 王五, 2026-04-26       │    ┌─────────────────┐                   │           │
│ 内容: 这个接口是异步的        │──→ │ [CONFLICT]       │ ── 保留双方       │ challenged│
│ 与已有快照矛盾                │    │ pending_resolution│    等待裁决       │           │
│                              │    └─────────────────┘                   │           │
│                              │                                          │           │
│ 来源: Agent 推断, 2026-04-27 │    ┌─────────────────┐                   │           │
│ 场景: 代码分析               │──→ │ 置信度: medium   │ ── 快照中标注      │  medium   │
│ 内容: 下游可能是库存服务      │    │ [待验证]          │                  │           │
│                              │    └─────────────────┘                   │           │
└──────────────────────────────┴──────────────────────────────────────────┴───────────┘

验证流转:
  unverified ──→ verified (team member confirms in code review)
  unverified ──→ challenged (someone raises objection)
  challenged ──→ resolved (conflict resolved, both versions kept with note)

Git review 机制:
  increment 文件随代码一起提交 → 天然支持 code review
  PR 中 .ai-context/increments/ 的变更可以被 review
  错误知识在 review 阶段被拦截
```

## 八、编辑前防护

```
┌─ 开发者要编辑文件 ────────────────────────────────────────────────────┐
│                                                                        │
│  Agent: 我想编辑 hooks/stop-flush.sh                                   │
│         ↓                                                              │
│  PreToolUse hook (pre-edit-guard.sh)                                   │
│         ↓                                                              │
│  搜索 .ai-context/snapshot.md + increments/                            │
│  找到 match → "hooks/stop-flush.sh" 有以下知识:                         │
│         ↓                                                              │
│  [CONSTRAINT] 阈值必须保持一致                                           │
│    - stop-flush.sh 和 config.yaml 中的阈值必须同步                       │
│    - 来源: 利普, 2026-04-23                                             │
│         ↓                                                              │
│  ⚠️ PRE-EDIT GUARD 提示:                                               │
│  "你即将编辑 stop-flush.sh。这个文件有以下知识关联..."                    │
│  "如果你要修改，请说明原因。你的解释将被记录为新的 DECISION。"             │
│         ↓                                                              │
│  Agent 看到提示 → 两种结果:                                             │
│    1. 理解了历史 → 决定不改（避免错误）                                   │
│    2. 确认要改 → 解释原因 → 原因自动写入 buffer → 知识更新                │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘

核心思想: 修改历史的人，必须先了解历史。修改行为本身又会产生新的知识。
```

## 六、核心原则

```
1. 知识是一等公民
   → 和代码同等待遇：版本化、可 review、可回滚、可协作

2. 零负担积累
   → 开发者不需要额外写文档，正常开发对话自动产生知识

3. 本地进化，全局传播
   → 通过 git 传播，不属于任何一个人

4. 快照只由编译产生
   → 不可直接编辑，保证质量一致性

5. 增量永不过期
   → 编译后归档，完整历史保留

6. 知识不丢失
   → 多道安全网：缓冲阈值 → commit 提取 → session 紧急 flush
```
